# Option C — Rauthy (IdP + agent credentials) + custom UI + 2fadod

## Tool research

**Rauthy** (`sebadob/rauthy`, Apache-2.0, audited by Radically Open
Security, alive): Rust IdP, no external DB by default (embedded Hiqlite),
passkey-first, ed25519 JWT signing with automated rotation. As an OIDC
provider it covers code flow + PKCE, device grant (nice for CLIs), DPoP,
token exchange — plus its own **forward-auth** (simple JWT mode and an
advanced encrypted-cookie + CSRF mode) for gating the UI.

⚠️ **Correction to our earlier assumption: Rauthy has NO API for minting
ephemeral passwords.** DeepWiki confirms: ephemeral auto-expiring passwords
are generated by a human in the account dashboard (`PamRemotePassword`
entity); API keys can manage PAM users but cannot mint ephemeral
credentials. So Rauthy **cannot** be the agent's short-lived-credential
issuer for autonomous use. Its PAM/NSS stack (`rauthy-pam-nss`, GPLv3,
separate repo) gates logins/SSH with MFA — not per-command approval — and
still needs a human at the dashboard for the ephemeral part.

Remaining role: Rauthy as the **SSO IdP for the approval UI** (light,
audited, forward-auth included), with agent identity coming from step-ca
as in A/B.

## Implementation plan

1. Rauthy in podman (single container, no Postgres needed). OIDC client
   entry for the approval UI; forward-auth advanced mode in front of it.
2. step-ca in podman for the agent certs (same flow as A/B) — Rauthy does
   not cover this.
3. `2fadod` + approval UI + pager script as in A/B, pointed at Rauthy's
   JWKS/issuer.
4. Ignore `rauthy-pam-nss` for v1 (login-gating, not command approval).

## Feasibility: MEDIUM-HIGH

Works, but Rauthy ends up being "Authelia-shaped with a nicer audit
report": an IdP + gate, nothing more. The ephemeral-password story that
made it exciting does not survive contact with the API docs. Choose it if
the audit + footprint matter more than Authelia's maturity; do not choose
it for agent credentials.
